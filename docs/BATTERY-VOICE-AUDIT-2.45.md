# Battery voice audit 2.45 — do the thirteen sentences sound like an owner?

Companion to [`BREAKAGE-2.45.md`](BREAKAGE-2.45.md). The principle under test (Ben, overnight brief): **owner prompts are the customer's dreams** — natural human Hebrew (and reasonable human English), never structured "LLM QA" language. The checks judge **site state after a reasonable human ask**, not whether the model obeyed a machine-formatted command.

Two things this file does:

1. **Audits** each of the thirteen prompts in `scripts/battery-copilot.js` (quoted exactly as `chat.say(…)` sends them) — is it owner voice, borderline, or QA voice — and proposes a reworded dream sentence where one is needed, saying whether the reword changes what the existing checks measure.
2. **Proposes new torture cases** in owner voice, only where the product already supports the behaviour, each with hard site-state checks, soft checks and the tool path it exercises. They are a **proposal table for Ben to pick from** — nothing here was added to `scripts/battery-copilot.js` (the sibling agent owns that file and it is mid-run).

What "owner voice" means here, so the verdicts are not taste: (a) the sentence names an **outcome the owner sees** (a button, a menu in one row, fewer typos), not a module or a tool; (b) it uses the words an Israeli small-business owner types into a chat — imperative-with-ת («תוסיף», «תשנה»), «לי», «משהו», a number when they care about the number; (c) it may be vague, may carry a typo or English loanword («CTA», «וואטסאפ»); (d) it never echoes the product's own vocabulary back at it («הפריט המסומן», «בלוק HTML», «קבץ לקבוצות») unless a real owner would have learnt that word from the builder. Where the current wording *does* echo product vocabulary, the audit says whether it matters: an echo makes the scenario **easier** than life (the model pattern-matches the briefing) and therefore hides a failure the owner would meet.

Everything about the *product side* of a proposed case was verified without a model on a scratch site (`/tmp/voice-verify*.js`, not in the repo) by calling the same door the copilot calls (`ai-tools.preflight`) and the same renderer (`pzn.compile`); the exact result is quoted.

**Tally** (fourteen sentences: T3 is two turns, plus the canned answer). 10 owner voice (T1, T2, T3b, T4, T5, T8, T10, T11, T12, T13; 11 with the canned answer), 1 borderline (T3a: builder jargon), **3 QA voice** (T6 echoes the situation block; T7 is a pen-tester's payload; T9 is the organizer's how-line). None of the three is *wrong* to keep — each measures a real door — but each is **easier than life**, and T6 is the one whose reword would change what a fail means for the programmer.

**A note on the English half of the principle.** The copilot's briefing is built with `locale:'he'` on every chat turn (`src/routes/copilot.js`, `buildCopilotBriefing({ locale: 'he', … })`) — the `en` locale exists for the paste/agent brief, not the copilot. An English-speaking owner therefore talks to a Hebrew-briefed model; the reply language is the model's choice. The proposals below include one English case for that reason, with a soft check on the reply language and no hard one.

## 3. What this audit could not verify

- Whether any of the proposed sentences changes a **model's** pass/fail: no model turn was spent on them (the sibling's battery owns the runtime). Every claim above is about the door and the renderer, checked directly.
- The reply language for N12: the copilot briefing is Hebrew-only by construction (`locale:'he'`), so an English reply is a model habit, not a product guarantee.
- Whether the Mac line's T6 fail was the echo or the pointer: the Mac JSON is not on this VM (see BREAKAGE §6 T6 for the deciding field).
